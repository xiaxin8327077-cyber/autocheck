# Auto Check 后续模块化开发规则（AI 开发必读）

状态：正式开发约束

适用项目：Auto Check（监管智核）

适用对象：后续参与新增功能模块、修改模块功能、审查模块代码的 AI 和开发人员

## 1. 使用方式

后续要求 AI 开发新模块时，应先向 AI 明确：

> 开始工作前，完整阅读并遵守 `docs/ai-modular-development-rules.zh-CN.md`。如果本次需求与该规则冲突，先停止开发并说明冲突，不得自行绕过模块边界。

本文件是模块化开发的统一执行规则。详细架构和实施依据为：

- `docs/superpowers/specs/2026-07-31-modular-extension-architecture-design.md`
- `docs/superpowers/plans/2026-07-31-modular-extension-host-implementation.md`

若规则发生冲突，按以下优先级处理：

1. 当前任务中用户明确提出的要求。
2. 仓库根目录及目标目录适用的 `AGENTS.md`。
3. 本规则文档。
4. 对应模块的设计文档和实施计划。
5. 现有代码中的历史实现方式。

任何冲突都必须在实施前说明。不得因为旧代码采用了集中式写法，就继续向公共大文件添加新模块业务代码。

## 2. 总原则

后续新增普通业务功能必须采用“平台内核＋独立模块”的方式开发。

每个模块应当拥有独立的：

- 后端入口、API、业务服务和数据协议。
- 前端入口、页面、组件、状态和样式。
- 数据库表和数据库迁移。
- 权限、导航和资源限制声明。
- 单元测试、接口测试、前端测试和验收测试。
- 设计、使用和运维文档。

模块之间通过平台公开协议通信，不得通过修改、导入或复制其他业务模块的内部代码完成需求。

模块化的目标是降低代码耦合、合并冲突和故障影响，但模块仍共享同一应用进程、数据库、磁盘、内存和网络资源，因此必须设置超时、并发、数据量和临时文件限制。

## 3. 开发前强制检查

AI 开始修改代码前必须完成以下检查：

1. 阅读本规则、适用的 `AGENTS.md`、模块设计文档和实施计划。
2. 检查 `git status --short`，识别用户已有改动和未跟踪文件。
3. 使用 `rg` 检索现有平台接口和相似模块，不凭记忆猜测接口。
4. 确认模块宿主是否已经完成并通过验收。
5. 明确本次改动是“普通模块改动”还是“平台协议改动”。
6. 列出本次允许修改的文件范围和禁止修改的公共文件。
7. 对非小型改动先形成方案并取得用户认可；小型、边界明确的模块内部改动可直接实施。
8. 明确测试范围、兼容性要求、数据库迁移影响和回滚方式。

如果模块宿主尚未完成，不得为单个业务模块私自在 `server.py`、`app.js` 或 `index.html` 中建立临时注册方式。应先按模块宿主实施计划完成平台能力，或向用户报告前置条件未满足。

## 4. 普通模块允许修改的范围

新增或修改普通模块时，默认只允许修改：

```text
src/auto_check/modules/<module_id>/
tests/modules/<module_id>/
docs/<module-related-document>.md
README.md                         # 仅在需要同步对外功能说明时
```

一个标准模块至少包含：

```text
src/auto_check/modules/<module_id>/
├── __init__.py
├── manifest.json
├── module.py
├── api.py
├── contracts.py
├── service.py
├── storage.py
├── migrations/
└── web/
    ├── index.js
    ├── styles.css
    ├── pages/
    └── components/
```

可以根据模块复杂度增加 `validator.py`、`executor.py`、`permissions.py`、`export_jobs.py` 等职责明确的文件。不得把全部业务逻辑重新集中到 `module.py`、`api.py` 或单个前端文件。

## 5. 普通模块禁止修改的范围

模块宿主完成后，普通模块开发原则上禁止修改：

- `src/auto_check/app/server.py`
- `src/auto_check/app/app_database.py` 中的全局业务表声明和全局 schema 版本
- `src/auto_check/web/index.html`
- `src/auto_check/web/app.js`
- `src/auto_check/web/styles.css`
- `src/auto_check/web/module_host.js`
- `src/auto_check/app/module_system/`
- 其他 `src/auto_check/modules/<other_module_id>/` 目录
- 其他模块的数据表、迁移、配置和测试
- Windows/Linux 打包脚本和公共部署脚本

禁止以下做法：

- 在 `server.py` 中增加模块专用 `if/elif` 路由分支。
- 在 `index.html` 中手工增加模块导航和页面容器。
- 在 `app.js` 中增加模块状态、接口调用和页面事件。
- 在全局 `styles.css` 中增加模块样式。
- 修改全局数据库版本常量来创建模块业务表。
- 直接导入其他模块的 `service.py`、`storage.py` 或内部类型。
- 为了复用而复制其他模块的大段内部实现。
- 使用其他模块的私有配置、临时目录、数据表或后台任务。
- 为单个模块临时修改打包规则。

## 6. 平台协议变更的例外流程

如果现有模块宿主确实无法支持业务需求，AI 不得在业务模块提交中直接修改平台内核，必须：

1. 明确指出缺失的平台能力和真实使用场景。
2. 证明该能力具有跨模块复用价值，而不是单一模块的便利需求。
3. 给出兼容性、安全、迁移、测试和回滚影响。
4. 单独编写平台变更方案，取得用户认可。
5. 在独立分支或独立提交中修改平台内核。
6. 先合并并验证平台兼容层，再开发依赖新协议的业务模块。
7. 平台接口版本发生不兼容变化时，按规则升级 `platform_api`，不得静默破坏已有模块。

平台变更不得夹带具体业务规则。`module_system`、`module_host.js` 和公共服务只能提供通用能力。

## 7. 模块清单和命名空间规则

每个模块必须提供 `manifest.json`，至少声明：

- `id`
- `name`
- `version`
- `platform_api`
- `required`
- `backend_entry`
- `api_prefix`
- `frontend_entry`
- `frontend_style`
- `navigation`
- `permissions`
- `dependencies`
- `schema_version`

命名规则：

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块 ID | 小写字母开头，只允许小写字母、数字、下划线 | `custom_reports` |
| API 前缀 | 模块独占，位于 `/api/modules/` 下 | `/api/modules/custom-reports` |
| 权限 | 使用模块 ID 前缀 | `custom_reports.view` |
| 数据库表 | 使用稳定模块前缀 | `custom_report_templates` |
| 静态资源 | 位于模块资源命名空间 | `/module-assets/custom_reports/index.js` |
| 事件 | 使用 `<module_id>:<event>` | `custom_reports:template_published` |
| DOM 根节点 | 使用模块 ID | `data-module="custom_reports"` |

模块 ID、API 前缀、导航 ID、权限、表名和公开服务必须全局唯一。发生冲突时应阻止冲突模块加载，不得覆盖已有注册。

新增普通业务模块默认必须设置 `required=false`，加载失败时只禁用当前模块，不得阻止核心系统启动。

## 8. 后端开发规则

模块入口必须遵守平台模块生命周期协议：

- `register_routes()`：注册模块相对路由。
- `register_schema()`：声明模块数据库结构。
- `start()`：启动模块服务和后台任务。
- `stop()`：停止任务并释放资源。
- `health()`：返回脱敏健康状态。

后端强制要求：

- API 只注册相对路径，由平台拼接模块 API 前缀。
- API 层只做请求解析、响应转换和状态码映射。
- 业务规则放在 service/validator 等模块内部服务中。
- 数据持久化放在 storage/repository 层，不在 API 处理器中直接拼接 SQL。
- 通过 `ModuleContext` 使用用户、数据库、配置、时间、日志、临时目录、事件和后台任务能力。
- 不持有或修改平台可变全局对象。
- 不调用其他模块或平台类的私有方法，例如以下划线开头的方法。
- 数据库查询必须参数化；标识符必须来自结构化白名单并按数据库方言引用。
- API 错误必须脱敏并带可追踪错误编号，不返回密码、连接串、SQL、驱动堆栈和本地绝对路径。
- 日志使用模块专属日志器，不记录密码、令牌和未脱敏敏感参数。

## 9. 前端开发规则

模块前端通过清单和宿主动态加载，必须实现：

- `mount(context)`
- `activate(route)`
- `deactivate()`
- `unmount()`

前端强制要求：

- 只能在宿主分配的模块根节点内查询和修改 DOM。
- 所有样式以 `.auto-check-module[data-module="<module_id>"]` 为顶层作用域。
- 禁止定义无作用域的 `button`、`input`、`table`、`.card` 等通用选择器。
- 不读取 `app.js` 中未声明为平台接口的变量和函数。
- 请求、会话、消息、确认框、路由和事件通过 `FrontendModuleContext` 使用。
- `deactivate()` 必须停止轮询和可取消任务。
- `unmount()` 必须清理事件监听器、定时器、轮询、AbortController 和临时 DOM。
- 页面只使用当前亮色活力主题和平台 CSS 变量。
- 主操作按钮可使用固定 Logo 蓝渐变 `#3466D9` 到 `#6AA4FF`；危险、警告、成功和中性操作按语义色显示。
- 控件使用全局圆角变量，如 `--ui-radius`，不得另建主题或圆角体系。
- 悬浮反馈不得使用主题光晕，只允许描边、轻微位移和必要的中性阴影。
- 警告和错误不得只用颜色表达，必须同时包含文字或图标。
- 模块 JavaScript/CSS 加载失败时只显示模块错误状态，不能影响其他页面。

## 10. 数据库和迁移规则

每个模块使用自己的 `migrations/` 目录和独立 schema 版本：

- 从 `001` 开始按顺序编号。
- 已发布迁移文件禁止修改，后续变化必须新增迁移。
- 迁移文件 checksum 与历史记录不一致时阻止模块加载。
- 同一模块迁移串行执行，并使用平台迁移锁防止并发执行。
- 迁移只允许操作本模块命名空间下的数据表。
- 不得修改其他模块或核心平台表。
- 迁移失败时禁用当前可选模块并记录脱敏错误。
- 停用或移除模块不得自动删除业务表和历史数据。
- MySQL 无法安全回滚的 DDL 必须在升级说明中明确备份和恢复步骤。
- 表结构变更必须同步仓储测试、迁移测试和运维文档。

禁止通过运行时 `CREATE TABLE IF NOT EXISTS` 隐藏未登记的正式迁移。

## 11. 权限、安全和资源规则

权限必须在后端执行，隐藏导航和按钮不能代替鉴权。

每个模块至少实施：

- 平台级模块权限校验。
- 资源级权限校验，例如所有者、可见范围、数据源范围和下载任务归属。
- 修改类请求的登录、CSRF 和请求体大小校验。
- 文件下载的登记路径、所有者和过期状态校验。
- 静态资源和文件路径的目录穿越防护。
- 数据库密码、连接串、会话令牌和敏感参数脱敏。
- 后台任务并发上限和单任务超时。
- 数据库查询超时、返回行数和导出行数上限。
- 模块专属临时目录、文件有效期和清理机制。
- 模块停止和应用退出时的资源释放。

模块只能加载随项目源码和安装包发布的可信代码。不得提供在线上传或执行第三方 Python/JavaScript 插件的入口；如果未来需要第三方插件，必须另行建设签名、权限声明、进程隔离和供应链安全方案。

## 12. 模块间通信规则

默认禁止模块直接导入另一个模块的内部文件。只允许：

1. 使用 `ModuleContext` 中的平台共享服务。
2. 使用经过版本声明的模块公开服务。
3. 使用命名空间事件总线发送不要求同步结果的通知。

公开服务必须声明名称、接口版本、是否必需和不可用时的错误行为。模块依赖不得形成循环。

事件负载必须可序列化。一个订阅者处理失败只能记录该订阅者错误，不得阻断其他订阅者。

跨模块共享需求优先抽象为只读、小接口、可版本化协议；不得为了少量复用暴露整个 service、storage 或数据库会话对象。

## 13. 故障隔离和生命周期规则

AI 必须验证以下行为：

- 可选模块导入、迁移或启动失败时，其他模块和核心功能仍可使用。
- 模块停用后不显示导航、不接受 API、不运行后台任务，但保留数据。
- 模块 API 异常转换为统一脱敏响应。
- 模块后台任务异常只终止当前任务。
- 模块前端加载或运行失败只进入模块错误页。
- 离开页面、切换会话、停用模块和关闭应用时正确清理资源。
- 模块重新启用后可以恢复正常服务，并正确处理进程中断遗留任务。

模块不得捕获异常后静默继续，也不得因单个可选模块失败而直接终止整个应用。

## 14. 测试和验证规则

每个模块必须提供：

- 清单和命名空间契约测试。
- API 登录、CSRF、权限和错误脱敏测试。
- 业务服务单元测试。
- 数据存储和迁移测试。
- 前端生命周期、DOM 和 CSS 作用域测试。
- 模块启停、失败隔离和资源释放测试。
- 与支持数据库、浏览器和打包方式相匹配的集成测试。
- 模块验收场景测试。

执行顺序：

1. 先运行本次变更直接相关的最小测试。
2. 再运行 `tests/modules/<module_id>/` 模块测试。
3. 合入前运行 `python -m pytest -q` 全量测试。
4. 运行 `git diff --check`，修复真实 whitespace error。
5. 只有用户明确要求打包、交付可执行程序或验证打包产物时，才运行打包脚本并刷新 `dist/auto-check.exe`。

测试和验证可清晰拆分时，优先交由子代理或后台任务执行；主会话负责检查结果、分析失败和进行必要补充验证。不得在没有实际测试输出的情况下宣称“测试通过”。

## 15. 文档和版本同步规则

新增或修改模块时必须同步：

- 模块设计文档和实施计划中的实际状态。
- 模块用户说明和运维说明。
- 数据库迁移、配置项、权限和容量边界说明。
- `README.md` 中的详细功能和行为变化。
- 受影响的自动化测试说明或验收场景。

模块更新日志规则（与 `AGENTS.md` 一致）：

- 模块更新点由平台聚合后并入系统应用内更新日志的最新系统版本条目，不单独成「模块更新」块，不单独展示模块版本号。
- 写入系统日志时的条目格式为「XX模块：具体内容」（`manifest.name`；末尾无「模块」时补「模块」）。
- 同一系统版本内不得出现重复条目；「系统优化及BUG修复」只由系统侧维护，模块 `release_notes.items` 不要再写该通用条。
- 展示用大版本号跨大版本变更必须由用户明确授权，模块与平台改动都不得自行推进大版本号。

普通模块不得为了更新系统日志而直接修改全局 `app.js`。模块通过 `manifest.release_notes` 提供条目，由平台合并展示；若需调整合并规则或展示格式，作为单独平台变更处理。

文档不得写入真实密码、令牌、生产连接串和未脱敏用户数据。

## 16. Git 和多人协作规则

- 每个模块使用独立功能分支或 worktree。
- 模块提交只包含本模块目录、对应测试和文档。
- 平台内核修改必须使用独立提交，不与业务模块混合。
- 不回退、不覆盖用户已有的无关改动。
- 不提交 `build/`、缓存、临时导出和本地测试数据等生成内容。
- 合并顺序为：平台兼容层、模块代码、集成验证。
- 多人并行时按文件职责划分，避免多人同时修改 `contracts.py`、`service.py`、`api.py`、`module.py` 等模块共享文件。
- 提交前检查差异范围，发现公共文件或其他模块被修改时必须解释原因；没有已批准的平台变更时应移除这些越界改动。
- 未经用户明确要求，不自动提交、推送或创建 Pull Request。

## 17. AI 完成任务前的强制自检

AI 在报告完成前必须逐项确认：

- [ ] 已完整阅读本规则和适用 `AGENTS.md`。
- [ ] 改动只位于批准的模块、测试和文档范围。
- [ ] 未修改公共入口、平台内核或其他业务模块；如有修改，已有独立批准记录。
- [ ] 模块清单、API、权限、表、事件、资源和 DOM 均使用模块命名空间。
- [ ] API、业务、存储、前端和迁移职责没有重新集中到单个大文件。
- [ ] 未直接依赖其他模块内部实现或平台私有方法。
- [ ] 登录、CSRF、资源权限、错误脱敏和资源限制已经实现并测试。
- [ ] 前端 DOM、CSS、事件、定时器和轮询受到模块边界约束。
- [ ] 数据库迁移独立编号，未修改已发布迁移。
- [ ] 模块失败、停用和卸载不会破坏其他功能。
- [ ] 已运行相关测试、模块测试和必要的全量测试。
- [ ] 已检查真实测试输出和 `git diff --check`。
- [ ] 未在用户未要求时自动打包、提交或推送。
- [ ] 已同步必要文档，并说明代码、配置、文档和行为变化。

任何一项无法确认时，不得宣称任务完成；应明确报告剩余工作、失败证据或阻塞条件。

## 18. 可直接复制给后续 AI 的任务前置指令

```text
本项目采用独立模块化开发。开始修改前，请完整阅读并遵守：
1. AGENTS.md
2. docs/ai-modular-development-rules.zh-CN.md
3. 当前模块对应的设计文档和实施计划

普通模块代码只能放在 src/auto_check/modules/<module_id>/，测试只能放在
tests/modules/<module_id>/。不得把模块业务代码写入 server.py、index.html、
app.js、styles.css、module_system 或其他业务模块。

如果现有平台接口不够用，请先停止业务实现，说明缺失能力，并提交独立的平台
变更方案；未经确认不得修改平台内核。实施完成后运行相关测试、模块测试、必要的
全量测试和 git diff --check。除非明确要求，不打包、不提交、不推送。
```
