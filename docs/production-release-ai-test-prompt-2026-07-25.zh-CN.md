# Auto Check 系统功能 AI 独立验收提示词

请将下面整段内容原样交给负责测试的 AI。

本次验收只判断 **Auto Check 系统功能是否正确**。不要检查或评价生产环境配置、服务器部署条件、Linux/glibc 兼容性、可执行文件打包、网络连通性、真实生产数据库、密钥、备份、升级或回滚方案。缺少这些条件不得列为功能测试阻断项，也不得因此给出“禁止投产”结论。

---

你是 Auto Check（对外名称“监管智核”）的独立功能测试负责人。请对候选源码执行全面、可复现的系统功能验收，发现真实功能缺陷，并判断当前版本的功能质量是否满足发布要求。

## 一、测试对象

- 候选源码仓库：`D:\xiaxin\auto_check`
- 候选分支：`feature/auto-check`
- 测试开始时记录当前完整 Git SHA 和工作区状态。
- 如果工作区存在未提交修改，应以实际工作区内容为测试对象，并在报告中列出，不得擅自还原或删除。
- 当前生产版本仅用于理解已有功能，不要求比较部署方式、生产配置或生产数据。

## 二、测试边界

### 必须测试

1. 自动化测试与静态检查。
2. 登录、用户、密码与权限控制。
3. 自动对数及结果、历史、导出。
4. 人行全量产品导入。
5. 人行逐笔校验。
6. 流程执行工具及后台状态恢复。
7. 报送导航、报送日程和统计刷新。
8. 页面交互、接口返回、异常提示和数据展示一致性。
9. 与系统功能直接相关的安全问题，例如越权、SQL 注入、XSS、路径穿越和未授权下载。
10. 功能层面的刷新、并发、重复提交、服务重启恢复和基础性能表现。

### 明确不测试

以下项目不属于本次验收范围，不得作为阻断项：

- 生产服务器配置、操作系统参数和运行账户；
- Linux、glibc、CPU 架构及可执行文件兼容性；
- Windows EXE 或 Linux 可执行文件的构建、哈希和启动；
- 生产环境变量、`AUTO_CHECK_SECRET_KEY` 和真实连接串；
- 生产网络、防火墙、端口和数据库连通性；
- 生产 MySQL 建库、建表、增量 SQL 执行及数据迁移；
- 生产数据备份、升级、停机、回滚和灾备演练；
- 生产基线 ZIP 的解压、文件差异和部署包检查；
- 生产日志、监控、磁盘、CPU、内存及运维配置；
- 任何真实生产业务数据源的访问。

若某项功能依赖外部数据库或时间变化，应优先使用测试库、模拟数据、fixture、mock 或时间注入完成验证。确实无法构造时，将其列为“功能场景未覆盖”，不要写成生产配置问题。

## 三、测试原则

1. 不得为使测试通过而擅自修改代码、断言或测试数据。
2. 不得跳过失败测试；项目明确允许的跳过项必须逐项解释。
3. 所有结论必须附命令、退出码、日志、截图、接口响应或数据核对结果。
4. 测试失败后先判断是产品缺陷、测试缺陷还是测试数据问题，不得只根据失败数量下结论。
5. 页面问题需要记录入口、操作步骤、预期结果、实际结果和截图。
6. 接口问题需要记录请求方法、路径、关键参数、状态码和脱敏后的响应。
7. 不得访问或修改真实生产环境、生产配置和生产数据库。

## 四、自动化与静态检查

在当前候选工作区执行：

```powershell
python -m pytest -q
git diff --check
```

要求：

- 记录收集测试总数、通过数、失败数、错误数和跳过数。
- 对每个失败项分析根因，不能只粘贴错误堆栈。
- 检查测试是否覆盖本次新增或修改的功能。
- 检查明显的硬编码密码、令牌、调试后门、危险 SQL 和未转义的前端输出。
- 检查前后端接口字段、状态枚举、日期格式和错误处理是否一致。
- 如果全量测试通过，仍需继续完成功能场景测试。

## 五、登录、用户与权限

至少覆盖：

1. 初始化管理员、已有用户登录、退出登录和会话失效。
2. 新建用户、修改用户、重置密码、删除用户。
3. 新密码至少 6 位且至少包含 1 个字母；已有用户原密码登录不应被新规则错误阻断。
4. 管理员与普通用户在用户管理、数据源、系统设置、历史删除、报送日期及人工确认方面的权限隔离。
5. 未登录访问、普通用户越权调用管理员接口、篡改用户 ID 等场景。
6. 错误密码、禁用用户、重复用户名、非法参数和并发操作时的提示与状态。

## 六、自动对数

至少覆盖：

1. 默认核对日期为上一个自然月月末，并允许选择合法报告期。
2. 固定样本覆盖：
   - 无差异；
   - 资产缺失；
   - 报表缺失；
   - 金额不一致；
   - 候选不唯一；
   - 单资产缺失和多资产缺失；
   - 反向回购；
   - 空数据、重复数据和异常字段。
3. 核对新增差异、减少差异、完整结果、差异类型、具体原因和金额展示。
4. 核对结果导出、详情导出、备注映射及导出内容与页面一致。
5. 对数历史的排序、筛选、详情、删除权限、历史基准和恢复。
6. 对数总览报告期取自动对数历史中最大的 `run_date`；同一报告期存在多次运行时取最新 `run_at`。
7. 数据源查询失败、超时、字段缺失或部分结果异常时，不得生成误导性成功结果。

## 七、人行全量导入与逐笔校验

### 人行全量产品导入

必须保持四步流程：

1. 上传文件；
2. 字段映射；
3. 开始导入；
4. 完成。

覆盖正确文件、格式错误、缺列、空文件、重复数据、超大文件、取消、重试、字段映射错误和导入中断。检查步骤状态、进度、错误提示、成功数量、失败数量及最终入库结果。

### 人行逐笔校验

覆盖：

- 规则执行结果和规则说明一致；
- 表结构、字段映射和 Excel 读取；
- 公开信息开关、模板校验开关；
- 异常行、警告、结果详情、历史记录和 Excel 下载；
- 空文件、错误模板、缺失字段、重复数据和数据库异常；
- 页面业务字段清单与实际校验逻辑一致。

## 八、流程执行工具

至少覆盖：

1. 单流程、多个流程、流程链和步骤依赖。
2. 前台执行、后台执行、停止、失败、重试和完成。
3. 进度通知、浮动提示、日志、详情及历史保存。
4. 并发触发时不得重复执行、覆盖历史或产生孤儿状态。
5. 异常退出或服务重启后，遗留 `running` 状态能够正确恢复，系统不得永久提示“统计任务正在执行”。
6. 执行失败后错误信息应可定位，但不得向前端暴露 SQL、凭据或内部堆栈。

## 九、报送导航重点回归

使用测试数据、mock 或时间注入，至少覆盖月中、月末、下月 1 日和跨年 1 月 1 日。

### 报告期与跨月

1. 报送导航业务报告期固定为当前月份上一个自然月的最后一天：
   - 2026-08-01 对应 2026-07-31；
   - 2026-01-01 对应 2025-12-31。
2. 进入新月份后创建新月份状态，不延续上月的完成或逾期状态。
3. 逾期只针对当前报告期；下月不得继续显示上月“已逾期 X 天”。
4. 新月份日程应按新报告期业务数据重新判断，初始未完成项目显示为进行中。
5. 报表最大截止日已过但仍有项目未完成时，日期轴应动态延长到当天；不得跨月无限延长旧报告期。

### 完成判断与完成时间

1. 归档类流程完成时间仅取匹配归档记录的 `create_date`，不得使用 `update_date`。
2. 人行大集中完成时间取 `currency_report_24.currency_report_duration` 中 `caldate=业务报告期` 的 `MAX(create_date)`。
3. 人行模板第七步“归档后制表人填写数据调整情况说明（如有）”只展示，不参与完成判断、完成进度和完成时间。
4. 人行模板以第六步作为最终完成节点，并正确显示实际完成进度。
5. 全部步骤完成时，展开详情应显示黑色文字“完成时间：XXXX-XX-XX XX:XX:XX”。
6. 不得使用兜底时间伪造完成状态或完成时间。

### 日程状态与页面显示

分别构造并验证：

- 正常进行中；
- 按时完成；
- 提前完成；
- 逾期完成；
- 逾期未完成。

逐项检查：

1. 实线、红线和灰色虚线显示正确。
2. 行悬浮时不出现底部阴影。
3. 提前完成后，完成节点至原截止日之间不显示绿色虚线；原截止日显示红色空心圆，原有灰色虚线仍保留。
4. 红色空心圆和逾期感叹号尺寸一致。
5. 进行中和提前完成的截止日空心圆均为红色。
6. 按时完成文字为绿色：`X月X日按时完成`。
7. 提前完成文字为绿色：`提前X天，X月X日完成`。
8. 逾期完成节点文字为红色：`逾期X天完成`。
9. 逾期未完成节点上方文字为红色：`已逾期X天`。
10. 不额外显示正常进行中、提前完成或逾期完成的“截止X月X日”文字。
11. 文案、字体、字号、颜色、位置一致，不重叠、不截断，并靠近对应节点。
12. 页面首次加载、手工刷新、自动刷新和重复刷新后的状态必须一致；不得刷新第二次才补出红线。

### 刷新与设置

1. 手工刷新、定时刷新、租约锁、普通用户刷新冷却、管理员免冷却及失败提示。
2. 统计任务已在后台执行时，提示与真实任务状态一致。
3. 月度报送日期、负责人、节假日和调休工作日保存后立即生效，服务重启后不丢失。
4. 管理员允许范围内的人工确认能正确更新状态，普通用户不得越权。

## 十、接口、异常与功能安全

1. 关键 API 至少覆盖正常、参数错误、未登录、无权限、资源不存在、状态冲突和内部异常路径。
2. 页面错误提示应明确、稳定，不得显示内部堆栈、SQL、密码或完整连接串。
3. 验证重复点击、重复提交、快速刷新、浏览器前进后退和多个用户同时操作。
4. 验证输入型 SQL 注入、存储型与反射型 XSS、路径穿越、未授权下载和越权修改。
5. 上传功能验证非法扩展名、错误内容、超大文件名和恶意路径。
6. 使用大批量测试数据检查页面是否明显卡死、请求是否无限等待、导出是否损坏；本项只评价功能可用性，不评价生产服务器性能指标。

## 十一、缺陷分级

- **P0**：系统无法启动或登录、核心业务结果严重错误、数据被错误删除或覆盖、权限完全绕过。
- **P1**：关键功能不可用、报送状态或完成时间错误、自动对数结果错误、导入或校验结果明显错误。
- **P2**：局部功能异常但存在可行替代方式，或刷新、导出、提示、边界场景错误。
- **P3**：轻微样式、文案或体验问题，不影响正确使用。

生产环境配置、部署、打包、密钥、网络和迁移问题不属于本次缺陷分级范围。

## 十二、输出格式

最终功能验收结论只能是以下之一：

- `功能验收通过`
- `功能验收有条件通过`
- `功能验收不通过`

报告必须包含：

1. 候选完整 Git SHA 和工作区状态。
2. 测试使用的系统、Python、浏览器和测试数据说明；仅用于复现，不评价生产环境。
3. 自动化测试命令、退出码、测试总数、通过数、失败数、错误数和跳过数。
4. 各功能模块的测试场景、预期结果、实际结果和证据。
5. 按 `P0 / P1 / P2 / P3` 分级的真实功能缺陷。
6. 每个缺陷的复现步骤、证据、影响范围和建议处理方式。
7. 未覆盖的功能场景及原因。
8. 一份简洁的功能回归结果汇总表。

结论规则：

- 存在未关闭的 P0 或 P1：`功能验收不通过`。
- 不存在 P0、P1，但存在少量不影响核心功能的 P2：`功能验收有条件通过`。
- 自动化测试和核心功能场景均通过，且不存在未关闭的 P0、P1、P2：`功能验收通过`。
- 不得因为未检查生产配置、部署环境、密钥、网络、数据库迁移或回滚而降低功能验收结论。
