# 报表特殊处理：数据治理负责人可改选全部用户

状态：已认可并实施

日期：2026-09-02

## 1. 目标

编辑/新建弹窗中，数据治理负责人在按「所属维度」自动带出后，允许从全部启用用户中改选。改维度时仍按新维度重新自动带出并覆盖当前选择。

确认权限规则不变：普通用户只能确认「数据治理负责人是自己」的记录。

## 2. 已确认需求

- 下拉名单改为全部启用用户（与「处理人」同源 `catalog.users`）。
- 自动带出仍只从该维度角色候选人中选取（项目/资产 → 数据治理_项目资产；资金/财务 → 数据治理_资金财务；多人则随机一人）。
- 改「所属维度」：按新维度重新自动带出，覆盖已选（含手动改过的人）。新维度无候选人则清空。
- 编辑已有记录：打开时保留已保存的人，不自动改。下拉仍是全量，可改选。若此人已不在启用名单，仍追加当前快照选项，避免空白。
- 新建：选维度后自动带出；名单始终是全量，可立刻改选。
- 确认弹窗只读，不改这项。
- 不改表结构、能力码、菜单、待办与通知规则。

## 3. 确认权限（本次不改，明确锁定）

现有规则保持不变：

1. 必须具备 `rsp.confirm`。
2. **管理员**（`role == admin`）可确认任意记录。
3. **非管理员**只能确认 `governance_owner_user_id` 等于自己用户 ID 的记录。

因此：数据治理用户 A 去确认数据治理用户 B 名下的记录时，**不能确认**。即使 A 也有确认能力、也属于数据治理角色，界面不出现「确认」，接口也会拒绝。本次把下拉改成全量用户，**不会**让同角色的人互相确认。

副作用（既有，不是新规则）：若手动把负责人改成没有 `rsp.confirm` 的用户，待办仍会发给此人，但此人无法完成确认（管理员仍可代确认）。

## 4. 方案选择

采用：一个原生下拉填全部启用用户；维度联动只改 `.value`（自动带出）。

未采用：分组下拉（推荐人在上、其他人在下）；单独「改选其他人」入口。

## 5. 模块边界

允许修改：

- `src/auto_check/modules/report_special_processing/web/components/record_drawer.js`（名单来源与联动）
- 模块 README、`manifest.json`（版本 `1.2.12`）
- `tests/modules/report_special_processing/`（前端静态；必要时补「保存非维度候选人仍成功」）
- 根 `README.md`、`src/auto_check/web/app.js` 更新日志小版本 `v1.2.21`（大版本仍为 `V1.2`）

禁止修改：

- `permissions.py` 的 `can_confirm`、待办查询、确认接口鉴权
- 平台内核、其他业务模块、能力码矩阵
- 数据库迁移

## 6. 测试要点

- 治理负责人下拉使用 `catalog.users`，不再只用 `governance_owner_candidates_by_dimension` 填选项。
- 维度变化仍读取候选人列表做自动带出（含随机）。
- 非管理员、非本条负责人：`can_confirm` 仍为 false（既有测试继续通过）。

## 7. 验收

1. 选维度后自动带出该维度候选人，可改选任意启用用户并保存。
2. 改维度后负责人被新维度自动带出覆盖。
3. 编辑打开不覆盖已保存负责人。
4. A 不能确认 B 名下记录；管理员仍可确认任意记录。
