# 报送管理独立模块设计

状态：用户已确认；Kettle 接口细节已按 2026-09-08 提供的 PDIA 10.1 REST API 文档补充

日期：2026-09-08

## 1. 目标

在监管智核中新增独立的“报送管理”模块，把监管报送过程中的报表生成、SQL 校验和报文生成整合到同一个业务入口，同时保持三类任务、记录和历史相互独立。

模块面向七类报送：

1. 人行大集中报送
2. 资管产品模板逐笔
3. 1104报送
4. 21/23版全要素报送
5. 中信登定期报送
6. EAST5.0报送
7. 五篇大文章报送

第一阶段建立七类报送共用的配置、混合流程和在线 SQL 校验能力，并以“资管产品模板逐笔”作为首个完整报文生成样板。其他六类在第一阶段可以配置、生成报表和执行校验，但只有后续补齐各自个性化报文契约后才能生成报文文件。

## 2. 已确认的业务原则

### 2.1 三类任务相互独立

- “生成报表”是执行由 KJB、KTR、Spider 组成的混合流程，目的是准备或更新监管报送平台数据库中的报表数据。
- “执行校验”是在规则绑定的数据源中执行问题明细 SQL，生成独立校验记录。
- “生成报文”是读取监管报送平台数据库的当前数据，依据表字段映射和当前报送的个性化格式器生成可下载文件。
- 三类任务不组成统一批次，不建立统一批次表。
- 三类记录只共同使用报送类型和报送期作为查询维度。
- 系统不判断底层数据是否已经变化，也不声称某次校验或某份报文必然对应某次报表生成后的数据状态。

### 2.2 生成与校验

- 生成报表时不自动生成报文文件。
- 生成页面提供“生成完成后自动执行校验”复选框，默认不勾选。
- 勾选后，只有报表生成成功才新建一条独立校验记录；该记录的触发方式为“报表生成后自动”。
- 用户可以在同一报送期手工执行多次校验，每次均形成独立记录。
- 手工校验支持执行全部已启用规则，或选择一个、多个校验分组。
- 自动校验固定执行当前报送下全部已启用规则。

### 2.3 报文与下载

- 生成报文不受校验结果限制，校验失败或尚未校验均不拦截生成和下载。
- 生成报文始终读取执行时监管报送数据库中的当前数据。
- 第一次操作显示“生成报文”，已有报文后显示“重新生成报文”。
- 每次生成都创建新的报文记录和文件版本，不覆盖旧文件。
- 支持单文件下载和整包下载。
- 历史报送期只允许查看记录和下载已有文件，不提供重新执行入口。

### 2.4 配置与报送期

- 配置按七类报送分别维护，不跟随报送期变化。
- 执行页只保留一个“报送期”，不再同时出现数据日期。
- 报送数据配置增加报送频率，支持月报、季报、半年报、年报和自定义频率。
- 上期、年初、上年末等校验参数由报送期和频率自动推导。

## 3. 接入方式与模块边界

### 3.1 独立业务模块

模块采用平台内核加独立模块的方式实现：

```text
src/auto_check/modules/regulatory_reporting/
├── __init__.py
├── manifest.json
├── module.py
├── api.py
├── contracts.py
├── service.py
├── storage.py
├── permissions.py
├── migrations/
├── mapping/
├── workflow/
├── validation/
├── message_export/
└── web/
    ├── index.js
    ├── styles.css
    ├── pages/
    └── components/
```

模块 ID 为 `regulatory_reporting`，名称为“报送管理”，API 前缀为 `/api/modules/regulatory-reporting`。模块设置 `required=false`，模块加载失败时不得阻止核心系统和其他模块启动。

普通业务代码不得写入 `server.py`、`app.js`、`index.html`、全局 `styles.css` 或其他业务模块。前端只通过模块宿主的 `mount`、`activate`、`deactivate` 和 `unmount` 生命周期接入，全部样式限制在：

```css
.auto-check-module[data-module="regulatory_reporting"]
```

### 3.2 需要先补齐的平台公共能力

现有模块宿主尚未公开本模块需要的全部通用能力。正式开发分成平台兼容层和业务模块两个独立提交，先完成并验证平台兼容层，再开发业务模块。

#### `platform.data_sources` v1

向模块提供：

- 脱敏的数据源目录，包括稳定 ID、名称和 PostgreSQL/MySQL 类型。
- 按数据源 ID 创建受限只读查询会话。
- 参数化查询、流式读取、查询取消、超时和最大返回量控制。
- 数据库标识符按方言引用与白名单校验。

该服务不向模块返回密码、完整连接串或核心配置可变对象。

#### `platform.flow_execution` v1

把现有 Spider 流程执行能力以版本化服务开放给模块：

- 按名称或流程 ID 查询现有 Spider 流程。
- 启动流程并返回外部任务编号。
- 查询状态、进度和增量日志。
- 请求取消本地等待及后续提交。
- 保持现有约束：取消不强杀已经提交到申报平台的 `sp_task`。

现有 `flow_tool.py` 和核心流程逻辑继续作为服务实现，不复制到报送管理模块。

#### `platform.kettle_execution` v1

Kettle 生产服务使用 HTTP Basic Auth，凭据由平台加密配置和保管，模块只能提交受控执行请求，不能读取用户名、密码或 Authorization 头。

当前文件系统模式调用为：

- KJB：`GET /kettle/executeJob/?job={远端路径}&{运行参数}`。
- KTR：`GET /kettle/executeTrans/?trans={远端路径}&{运行参数}`。
- 未被保留的其他 query 参数作为 Kettle 变量传入；参数名和值必须 URL 编码。
- 不使用 `user`、`pass` query 参数传递认证信息。

平台服务通过 `jobStatus/transStatus` 查询状态和增量日志，通过 `stopJob/stopTrans` 请求停止。启动成功后优先保存返回的 Carte ID，后续查询和停止同时传 name 与 id。PDIA 10.1 文档说明 `executeTrans` 成功时可能返回空响应，因此真实联调必须确认当前 Pentaho 11 服务是否返回 ID；若无法取得唯一 ID，不允许相同 KTR 并发执行，也不得把按名称查询到的“最近一次执行”误判为当前任务。

接口依据为用户提供的 `PDIA_REST_API_10_1_MK-95PDIA010-01 (1).pdf`，实施时还要在 Pentaho 11 测试环境验证兼容性，不能仅凭 10.1 文档认定行为一致。

#### `platform.artifact_storage` v1

错误明细和报文文件要求永久保留，而现有 `ModuleContext` 只提供临时目录。平台新增模块隔离的持久文件服务：

- 按模块和业务键保存、读取文件。
- 返回不含绝对路径的稳定文件标识。
- 保存文件大小、SHA-256、内容类型和创建时间。
- 支持流式写入、范围读取和完整性校验。
- 强制模块命名空间、目录穿越防护和容量统计。
- 第一阶段不自动清理报送管理文件。

模块数据库只保存文件标识及元数据，不保存平台物理路径。

### 3.3 复用现有报送导航

模块通过 `platform.report_navigation` v1 获取七类报送的稳定编码和显示名称，不在前端或业务服务中维护第二份报送名单。运行记录同时保存报送编码和名称快照，确保历史名称不随导航调整而变化。

## 4. 页面与交互

### 4.1 总体结构

“报送管理”作为一个顶部业务导航入口。模块内部只保留三个主页签：

1. 报表生成
2. 报表校验
3. 配置管理

三个页面左侧均保留七类报送选择。页面布局、亮色主题、Logo 蓝渐变 `#3466D9` 到 `#6AA4FF`、语义色和全局圆角遵循现有项目规范，不新增主题切换。

不提供单独的“报文下载”和“执行历史”页签。报文下载并入生成记录，生成历史和校验历史分别放在对应页面。

### 4.2 报表生成页

顶部操作区包含：

- 报送期。
- “生成完成后自动执行校验”复选框。
- “生成最新报文”次操作按钮。
- “生成报表”主操作按钮。

执行区包含：

- 当前混合流程的步骤顺序。
- 每一步的 KJB、KTR 或 Spider 类型。
- 等待、运行中、成功、失败、已跳过和已取消状态。
- 执行进度、开始时间和耗时。
- 当前任务的实时增量日志。

最近生成记录包含：执行时间、报送期、结果、步骤完成情况、报文文件数量、操作人和操作。操作包括查看日志、生成或重新生成报文、查看文件和下载报文。

当所选报送尚未安装个性化报文格式器时，页面明确显示“该报送的报文格式尚未接入”，隐藏生成报文操作，但不影响生成报表和执行校验。

### 4.3 报表校验页

顶部操作区包含报送期、校验分组多选和“开始校验”。结果区展示：

- 规则总数。
- 已完成规则数。
- 通过规则数。
- 不通过规则数。
- 执行异常规则数。
- 错误明细总行数。

规则结果列表展示规则编号、名称、大类、细类、规则标识、分组、状态、错误条数、耗时和查看明细。错误条数可点击。

错误明细弹窗的列来自规则保存的展示字段。查询 SQL 例如返回 `a,b,c,d` 时，页面自动形成四列；若用户在规则配置中取消 `c`，结果仍完整保存，但界面只展示 `a,b,d`。弹窗采用服务端分页，不一次性加载全部错误数据，并支持下载当前规则的完整错误明细。

页面下方显示所选报送期的历次校验记录。同一报送期多次执行时按时间倒序分别展示，不与生成记录合并。

### 4.4 配置管理页

配置管理不显示报送期，只按左侧所选报送维护长期配置。内部固定为三个子页签。

#### 报送数据配置

主配置只维护：

- 报送编码。
- 数据源 ID。
- 分类编号。
- 报送频率。

表 ID 不由用户填写，而是通过分类编号从报表信息表查询取得。保存配置后自动刷新一次映射，同时保留“刷新映射”按钮。

同一页面提供映射状态、查看表映射、查看字段映射和查看跨表映射入口。自动匹配方式与现有人行逐笔校验引擎保持一致。映射明细允许按现有方式人工覆盖或恢复自动映射，但不要求管理员逐张表、逐字段录入。

#### 流程编排

一条报表生成流程可自由混排：

- Kettle 作业 `.kjb`。
- Kettle 转换 `.ktr`。
- 现有 Spider 流程。

每一步配置名称、类型、远端作业或流程标识、顺序、是否启用、参数映射、超时和失败策略。失败策略为“失败后停止”或“记录失败后继续”，默认失败后停止。

#### 校验配置

页面包含规则分类、规则分组、参数定义和规则列表。规则支持新增、查看、编辑、启停、试运行和查看操作记录，不提供面向生产用户的批量导入入口。

## 5. 报文映射与生成

### 5.1 映射生成流程

报送表字段映射只用于生成报文，不参与 SQL 校验。刷新流程为：

```text
报送编码、数据源、分类编号
  → 查询报表信息表
  → 获得该分类下全部表 ID
  → 查询字段信息表
  → 获得字段中英文名称和顺序
  → 校验实际物理表字段
  → 生成完整映射快照
  → 在一个事务中切换当前快照
```

刷新失败时不保存半成品，不覆盖上一份成功快照。报文任务启动时锁定当前映射快照，后台刷新不得改变正在执行的任务。

映射快照至少保存：

- 报送编码、数据源 ID、分类编号。
- 映射来源表配置。
- 表 ID、表中文名、表英文名和物理表名。
- 字段 ID、字段中文名、字段英文名、实际物理字段、顺序和数据库类型。
- 自动匹配值、人工覆盖值、最终生效值和映射状态。
- 快照生成时间、操作人和来源配置版本。

### 5.2 个性化报文格式器

公共导出框架负责：

- 取得报送配置和不可变映射快照。
- 按报送期流式读取当前数据。
- 文件版本、临时生成、结构检查、持久化和下载。
- 文件大小、哈希、创建人和生成时间登记。

每类报送由独立的内置格式器负责文件格式、编码、表头、字段顺序、空值、命名、工作表和压缩目录。系统不提供在线上传或执行 Python、JavaScript 等第三方脚本的入口。新增或修改个性化格式器必须随模块代码评审和发布。

第一阶段只有“资管产品模板逐笔”安装完整格式器。其输出契约只适用于该报送，不作为其他六类报送的通用格式。该格式器沿用已确认的 `docs/superpowers/specs/2026-09-03-db-validation-message-export-design.md`：生成 14 个逐笔 `.xlsx`、2 个模板 `.xls`，合计 16 个文件，并遵守其中的文件名、目录、工作表、字段顺序和格式要求。

### 5.3 报文原子性

- 所有要求的文件均成功生成并通过格式器结构检查后，才形成可下载版本。
- 任一文件失败时，整次报文任务失败，不提供残缺压缩包。
- 失败任务保留脱敏状态和日志，不登记为成功报文版本。
- 历史成功文件永久保留，重新生成不覆盖旧版本。

## 6. 混合流程执行

### 6.1 统一步骤协议

模块内部定义统一步骤适配器：

```text
start(step, execution_context) -> external_task_reference
poll(external_task_reference) -> status, progress, incremental_logs
cancel(external_task_reference) -> cancel_result
```

KJB 和 KTR 适配器调用 `platform.kettle_execution`，Spider 适配器调用 `platform.flow_execution`。模块只保存远端标识、平台任务 ID、脱敏请求快照、状态和日志，不保存 Kettle 密码、Authorization 或 Spider 会话内部对象。

### 6.2 执行上下文

每次生成任务创建不可变上下文，至少包含：

- 报送编码和名称快照。
- 报送期。
- 报送配置版本。
- 流程定义及步骤快照。
- 运行参数及格式化结果。
- 操作人和触发时间。
- 是否在成功后自动创建校验任务。

页面关闭不会停止任务。重新进入页面后通过持久运行记录恢复进度和日志。应用重启时，本地未完成任务先标记为“执行中断”；如果步骤已提交到 Kettle 或 Spider且保存了外部任务编号，恢复程序尝试查询最终状态，但不重复提交同一步骤。

## 7. SQL 校验规则

### 7.1 规则字段

每条规则保存：

- 规则 ID、规则编号和规则名称。
- 规则大类和规则细类。
- 规则标识，默认字典为错误、警告和提示。
- 校验分组。
- 数据源 ID。
- 是否启用。
- 规则说明。
- SQL 正文。
- 自动识别的涉及源表。
- 自动识别并经用户取舍后的展示字段。
- 当前修订号、创建人、修改人和修改时间。

不设置自定义 SQL 开关、定位字段、权重、生效日期或失效日期。规则保存后长期生效，只有用户主动设为“不启用”才停止执行。错误、警告和提示只影响结果分类与展示，不拦截报文生成或下载。

### 7.2 SQL 安全契约

- 规则必须是单条只读 `SELECT` 或 `WITH ... SELECT`。
- 禁止 DML、DDL、事务控制、会话设置、多语句和数据库侧文件操作。
- 数据库连接使用规则绑定的数据源，不根据 SQL 内容自动切换数据源。
- 更换数据源只修改规则的数据源 ID，不批量替换 SQL 中的库名、schema 或表名前缀。
- SQL 校验不读取、转换或依赖报文表字段映射。
- 保存、试运行和正式执行均应用查询超时、只读会话和结果限制。

### 7.3 参数

SQL 使用 `${xxx}` 占位符。系统内置：

- `${report_period}`
- `${report_period_yyyymmdd}`
- `${report_period_yyyymm}`
- `${previous_period}`
- `${previous_period_yyyymmdd}`
- `${year_begin}`
- `${previous_year_end}`

校验配置允许按报送新增自定义参数，保存参数编码、中文名称、数据类型、取值规则、格式和预览值。执行前必须解析全部占位符；存在未定义参数时拒绝启动对应规则。

值位置的参数转换为数据库绑定参数。用于动态表名等标识符位置的参数只允许来自系统派生值或受控枚举，并通过严格字符白名单和数据库方言引用后使用，不接受任意用户输入。

### 7.4 展示字段快速识别

SQL 或数据源发生变化时，保存前执行零数据包装查询：

```sql
SELECT * FROM (<用户 SQL>) ac_meta WHERE 1 = 0
```

实际语法由 PostgreSQL/MySQL 方言适配器生成。数据库只完成语法解析并返回列结构，不读取错误明细。数据库返回的字段名或别名是展示字段的权威来源；静态 SQL 解析只负责识别涉及源表和阻止危险语句。

识别结果按数据源 ID、SQL 哈希和参数定义哈希缓存。内容未变化时不重复查询。展示字段重名、为空或不合法时要求用户为 SQL 增加明确别名。

字段变化时：

- 原来仍存在的字段保留用户的显示或隐藏选择。
- 新增字段默认显示。
- 已从 SQL 删除的字段自动移除。

### 7.5 试运行

试运行解析用户选择的测试报送期和 `${xxx}` 参数，通过方言适配器在外层限制最多 5 行。等价目标为：

```sql
SELECT * FROM (<用户 SQL>) ac_trial LIMIT 5
```

试运行只展示最多 5 条示例数据，不计算完整错误条数，不保存错误明细，不写校验历史。试运行默认超时 10 秒。

### 7.6 正式执行

正式校验启动时保存报送、报送期、选择的分组、参数、规则列表、规则修订和 SQL 快照。每条规则执行约定为：

- 返回 0 行：通过。
- 返回一行以上：不通过。
- 返回总行数：错误条数。
- 返回字段：完整错误明细。
- SQL 抛错或超时：执行异常。

单条规则异常不终止其他规则。结果列表分别统计通过、不通过和异常，不能把异常当作通过。

### 7.7 初始规则装载

生产配置页面不提供批量导入。开发开始前，用户提供 Excel 或 SQL 文件作为首次规则初始化来源。开发阶段执行一次受控转换：

- 将规则编号、名称、分类、分组、数据源和 SQL 转换为版本化初始化数据。
- 校验规则编号唯一、数据源存在、SQL 为只读查询且参数已定义。
- 初始数据随模块迁移或受版本控制的种子迁移交付。
- 上线后通过单条规则配置维护，不执行运行时上传文件或任意脚本。

## 8. 历史与永久明细

### 8.1 记录模型

生成、校验和报文分别保存：

- `regulatory_reporting_generation_runs`、`generation_steps`、`generation_logs`
- `regulatory_reporting_validation_runs`、`validation_rule_results`
- `regulatory_reporting_message_runs`、`message_files`

不存在统一轮次或批次表。自动校验记录可保存触发生成记录 ID 作为来源说明，但查询、状态和生命周期仍完全独立。

### 8.2 错误明细

错误汇总保存在应用数据库，完整动态明细保存在 `platform.artifact_storage`：

- 按报送、报送期、校验记录和规则分区。
- 按固定行数写成独立压缩分块。
- 每个分块登记起止行号、行数、字节数和 SHA-256。
- 数据库保存列定义、分块索引和完整错误行数。
- 页面根据页码只读取覆盖当前页的分块。
- 下载完整错误明细时按顺序流式合并，不把全部数据读入内存。

历史记录和错误明细第一阶段永久保留，不提供删除入口，也不运行自动清理任务。运维备份必须同时覆盖应用数据库和平台持久文件目录。

## 12. 并发、超时和资源限制

默认值如下，实施时作为可验证的模块配置提供：

| 项目 | 默认值 |
| --- | ---: |
| 同一报送的活跃生成任务 | 1 |
| Kettle 全局并行步骤 | 2 |
| Spider 全系统并行步骤 | 1，沿用现有限制 |
| 同一报送的活跃校验任务 | 1 |
| 全局并行校验任务 | 2 |
| 单数据源并行 SQL | 4 |
| 全局并行 SQL | 16 |
| 单条正式 SQL 超时 | 120 秒 |
| 试运行超时 | 10 秒 |
| 展示字段识别超时 | 5 秒 |

校验按数据源分组并使用独立信号量。停止校验后不再提交新规则；已经执行的查询通过数据源服务请求取消，无法取消时等待单条超时。报文查询和文件写入使用流式接口，禁止把整张大表或全部错误明细一次性放入内存。

## 13. 操作记录

规则操作记录的展示方式参照“报表特殊处理”模块：

- 主行显示操作时间、操作人、操作类型和变更项数量。
- 点击“查看变更详情”后展示“字段、修改前、修改后”三列。
- SQL 只显示开头预览，可展开并复制完整 SQL。
- 规则分类、分组、数据源、启用状态、SQL、自动识别源表和展示字段变化均进入差异。
- 创建、修改和启停均保留；规则不做物理删除。
- 旧修订不可改写，校验历史通过修订号还原当时规则。

报送数据配置和流程配置使用同样的审计数据结构，但由本模块自行实现，不导入或复制“报表特殊处理”模块的内部前端或业务代码。

## 14. 故障处理与生命周期

- 可选模块导入、迁移、启动或前端加载失败时，只禁用报送管理。
- 映射刷新失败时保留上一份成功快照。
- 流程步骤失败按步骤策略停止或继续，默认停止。
- 单条规则失败记录为异常，不阻断其他规则。
- 报文生成失败时不提供残缺文件。
- 离开模块页面时停止前端轮询和监听，但不停止后台任务。
- 重新进入页面后恢复活动任务状态。
- 模块停用或应用关闭时停止提交新任务、取消队列并释放线程、数据库会话和文件句柄。
- 模块停用不删除配置、历史、错误明细或报文文件。
- 外部 Kettle/Spider 状态无法确认时标记为“状态待确认”，不猜测成功，也不自动重复提交。

## 17. 部署与回滚

- 数据库迁移只新增模块命名空间表，不修改其他模块表。
- 平台公共服务保持向后兼容，不改变现有核心 API 和流程工具行为。
- 模块为可选模块，关闭模块或移除导航权限即可停止新入口。
- 回滚应用版本前停止新任务，等待或人工确认 Kettle、Spider 和校验任务状态。
- 回滚不删除模块表和持久文件；旧版本忽略新增数据。
- 上线前必须备份应用数据库和持久文件目录，并验证恢复方式。

## 18. 非目标

- 不在现有报送导航页面执行生成、校验或下载操作。
- 不建立统一“轮次”或统一批次。
- 不自动判断底层数据是否变化。
- 不用校验结果拦截报文生成或下载。
- 不提供生产界面的 Excel/SQL 批量导入。
- 不自动修改 SQL 中的库名、schema 或表名前缀。
- 不提供任意脚本上传、在线 Kettle 设计器或 KJB/KTR 文件编辑器。
- 不在第一阶段实现另外六类报送的个性化报文格式器。
- 不提供历史记录和错误明细删除功能。
- 不修改展示用大版本号，不自动打包、部署、提交或推送代码。
