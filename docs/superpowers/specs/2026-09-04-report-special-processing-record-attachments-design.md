# 报表特殊处理记录附件设计

状态：已确认，待实施

日期：2026-09-04

## 1. 目标

在“报表特殊处理录入”的新建、保存草稿和编辑抽屉中增加记录级附件能力。用户可以直接粘贴剪贴板中的文件或通过文件选择器上传图片、Excel、Word 和 ZIP。保存后可在记录详情中预览图片、下载全部支持类型，并在操作记录中查看每次附件修改前后的完整附件集合。

附件属于报表特殊处理记录本身，与现有“确认完成时粘贴图片”的确认附件分开管理。

## 2. 已确认需求

- 附件入口位于报表特殊处理记录的新建和编辑抽屉。
- 支持两种添加方式：直接粘贴和点击上传。
- 支持 PNG、JPEG、WebP、XLS、XLSX、DOC、DOCX、ZIP。
- 每条记录当前最多 10 个附件，单个最多 10 MiB，当前附件总计最多 30 MiB。
- 新建、保存草稿和编辑均可保存附件。
- 修改附件也属于记录修改，必须递增 `row_version` 并生成修改审计。
- 操作记录可以查看该次修改前和修改后的完整附件集合。
- 从当前记录移除的附件仍需保留，供历史操作记录预览或下载。
- 当前记录整体删除时，才删除该记录全部当前附件和历史附件。
- 现有确认说明图片附件继续保持原行为和数据结构，不迁移、不混用。
- 本功能与“登录超时原账号重新认证与原操作恢复”一同交付；登录超时后，尚未保存的附件仍保留在当前标签页并随原保存请求自动续传一次。

## 3. 非目标

- 不提供附件在线编辑、Office 在线预览、ZIP 解压或内容检索。
- 不提供附件重命名、拖拽排序、分片上传、断点续传或跨记录复用。
- 不支持 SVG、XLSM、DOCM、RAR、7Z、可执行文件或其他未列明类型。
- 不新增菜单、页面入口、权限码、平台文件服务或外部对象存储。
- 不把未保存附件写入 localStorage、sessionStorage 或临时磁盘。
- 不为历史记录提供独立的附件恢复到当前记录功能；如需恢复，用户重新添加文件。

## 4. 方案选择

采用“模块数据库内不可变附件 + 记录保存时原子提交”方案：

- 新文件以 Base64 包含在新建或修改 JSON 请求中。
- 当前已经存在且继续保留的附件只提交附件 ID，不重复提交文件字节。
- 附件原始字节存储在模块自有 `LONGBLOB` 表中。
- 附件内容和元数据创建后不可覆盖；同名文件的新版本创建新的附件 ID。
- 从当前集合移除时只标记移除，不立即删除内容。
- 记录主数据、附件增删和审计日志在同一数据库事务内完成。

未采用的方案：

1. 先上传临时附件、再保存记录：更适合超大文件，但需要临时凭证、孤立文件清理、过期策略和两阶段一致性，本需求的 30 MiB 总量不需要该复杂度。
2. 文件落磁盘、数据库只存路径：会增加 Windows/Linux 路径、备份恢复、权限和多实例一致性问题，不符合模块现有自包含存储模式。
3. 每次修改复制全部附件快照：查询简单，但会反复复制未变化的大文件，数据库增长不可控。

原始附件上限 30 MiB，经 Base64 后约为 40 MiB；加上记录 JSON 元数据后，路由请求上限设置为 45 MiB，低于平台 50 MiB 上限，不修改模块宿主协议。

## 5. 模块边界

这是报表特殊处理模块的业务能力，改动应主要限制在：

- `src/auto_check/modules/report_special_processing/`
- `tests/modules/report_special_processing/`
- 模块正式说明、根 README、版本日志及迁移清单测试

附件功能自身不修改 `server.py`、模块宿主、`module_host.js`、其他业务模块或平台权限矩阵。与其一同交付的登录超时需求仍按独立设计文档允许对 `server.py` 做专用认证响应头的单点修改：

- `docs/superpowers/specs/2026-09-04-session-expiry-reauthentication-design.md`

不得把附件校验、附件表或报表特殊处理业务规则写入平台 `app.js`、`auth_recovery.js` 或 `server.py`。

## 6. 用户交互

### 6.1 新建与编辑抽屉

在记录表单中增加“附件”区域，适用于新建、保存草稿和可编辑记录：

- 标题显示“附件（选填）”。
- 提示“支持直接粘贴，或点击上传；最多 10 个，单个 10 MiB，总计 30 MiB”。
- 提供“上传附件”次要按钮和隐藏的 `input[type=file][multiple]`。
- `accept` 只列出已允许扩展名和 MIME 类型。
- 抽屉监听 `paste`；只有剪贴板包含受支持文件时才拦截默认行为，纯文字粘贴继续进入当前文本框。
- 文件从资源管理器复制后，仅在浏览器暴露 `clipboardData.files/items` 时支持粘贴；不支持时提示改用上传按钮。
- 截图或无文件名图片自动命名为 `粘贴图片-YYYYMMDD-HHmmss-N.<服务端允许的图片扩展名>`；常见截图为 `.png`。

待保存附件使用文件卡片展示：

- 图片显示缩略图、文件名和大小，点击缩略图打开大图预览。
- Excel、Word、ZIP 显示对应文件图标、原文件名和大小。
- 每个附件提供危险语义的删除按钮。
- 同一当前附件集合中，内容 SHA-256 相同的文件只保留一个并提示“该附件已添加”；前端哈希属于即时反馈，浏览器不支持时仍由后端最终拦截。
- 同名但内容不同的文件允许同时存在，以附件 ID、大小和添加时间区分。
- 不提供重命名和排序；统一按 `created_at ASC, id ASC` 展示，已存在附件保持原创建顺序，同一请求内共享创建时间的新附件由自增 ID 保证添加顺序。

### 6.2 详情与只读状态

- 详情抽屉展示当前附件列表。
- 图片可打开模块内大图层；大图层支持关闭按钮、点击遮罩和 Escape。
- Excel、Word、ZIP 不在线打开，只提供下载。
- 已完成和已作废记录的附件区域只读。
- 记录重开后恢复编辑能力，可以增删当前附件；原历史附件仍保留。

### 6.3 操作记录

附件集合变化时，该条“修改”操作记录增加“附件”字段，展开后使用“修改前 / 修改后”双栏：

- 两栏均展示当时完整附件快照，而不仅展示文件名差集。
- 附件标注“新增”“移除”或“保留”；标签必须由该条审计自己的 `old_ids/new_ids` 集合差计算，不能读取附件行当前的 `removed_at` 推断历史状态。
- 图片在两栏中均可预览；全部附件均可下载。
- 同名不同内容通过附件 ID、大小和添加时间区分。
- 如果附件集合未变化，该次审计不显示附件字段。
- 只修改附件时，操作摘要显示“修改附件（新增 N 个，移除 M 个）”。

现有确认完成操作中的 `confirm_attachments` 仍按确认图片缩略图展示，不改为上述双栏，也不计入记录附件数量。

### 6.4 视觉与可访问性

- 使用现有亮色活力主题、全局 `--ui-radius` 和主题色变量。
- 上传按钮为次要操作，不使用渐变；保存按钮继续使用现有主操作样式。
- 删除附件使用红色危险语义。
- 文件卡片悬浮仅使用描边和轻微位移，不使用主题光晕。
- 上传按钮、删除按钮、大图预览和错误提示具有明确的 aria-label、键盘焦点和可读状态。

## 7. 数据模型

新增迁移 `006_record_attachments.sql`，新增表 `report_special_processing_record_attachments`：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 附件主键 |
| `record_id` | BIGINT | 所属报表特殊处理记录 |
| `original_file_name` | VARCHAR(255) | 清理路径后的原文件名或生成名 |
| `file_extension` | VARCHAR(16) | 规范化小写扩展名 |
| `content_type` | VARCHAR(128) | 服务端确认后的 MIME 类型 |
| `byte_size` | INT | 原始字节数 |
| `content_sha256` | CHAR(64) | 原始内容 SHA-256 |
| `content` | LONGBLOB | 原始文件字节 |
| `created_by_user_id` | VARCHAR(64) | 添加人用户 ID |
| `created_by_username_snapshot` | VARCHAR(100) | 添加人用户名快照 |
| `created_at` | DATETIME(6) | 添加时间 |
| `removed_by_user_id` | VARCHAR(64) NULL | 从当前集合移除的操作人 |
| `removed_by_username_snapshot` | VARCHAR(100) NULL | 移除人用户名快照 |
| `removed_at` | DATETIME(6) NULL | 移除时间；NULL 表示当前附件 |

索引与约束：

- 主键 `id`。
- 索引 `(record_id, removed_at, created_at, id)`，用于按 `created_at, id` 稳定读取当前附件。
- 索引 `(record_id, content_sha256)`，用于当前集合内容去重和历史查询。
- 不使用 `(record_id, original_file_name)` 唯一约束，因为允许同名不同内容。

表中附件行不可更新内容、文件名、类型、大小或哈希；允许的更新只有首次设置移除人和移除时间。附件被重新添加时创建新行，不恢复旧行。

模块 `schema_version` 从 5 升到 6。已发布迁移 `001`–`005` 不修改。

## 8. API 契约

### 8.1 新建与修改请求

沿用：

- `POST /records`
- `PUT /records/{id}`

请求增加可选字段：

```json
{
  "record_attachments": {
    "retained_ids": [12, 13],
    "new_files": [
      {
        "client_id": "local-1",
        "file_name": "处理依据.xlsx",
        "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        "data_base64": "..."
      }
    ]
  }
}
```

语义：

- 新建时 `retained_ids` 必须为空。
- 修改时 `retained_ids` 只能引用该记录当前未移除的附件，不能引用其他记录或历史已移除附件。
- `new_files` 只包含本次新增文件。
- 新建请求省略整个 `record_attachments` 字段时等同于没有附件，保持现有调用方兼容。
- 修改请求不包含 `record_attachments` 时，附件集合保持不变，兼容现有调用方。
- 修改请求明确包含 `{ "retained_ids": [], "new_files": [] }` 时，移除全部当前附件。
- 一旦提供 `record_attachments`，其值必须是对象，且 `retained_ids` 和 `new_files` 两个数组都必须显式提供；空对象、缺少任一数组、数组内重复 retained ID 或类型不正确均返回 400，不做隐式默认。
- `client_id` 只用于把后端字段错误映射回前端卡片，不入库。
- 路由完成服务端校验后，响应返回当前附件元数据列表，不返回 `content` 或 Base64。
- POST 和 PUT 的 `max_body_bytes` 使用独立常量 45 MiB；其他模块路由上限不变。

附件元数据响应结构：

```json
{
  "id": 14,
  "file_name": "处理依据.xlsx",
  "file_extension": ".xlsx",
  "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "byte_size": 182340,
  "content_sha256": "...",
  "created_by": { "user_id": "...", "username": "..." },
  "created_at": "2026-09-04T10:30:00+08:00",
  "removed": false
}
```

### 8.2 详情与审计

- `GET /records/{id}` 的记录对象增加当前 `record_attachments` 元数据数组。
- `GET /records/{id}/audit` 在读取分页审计时批量收集 `old_ids/new_ids`，一次性查询附件元数据并补全双栏快照，避免逐附件 N+1 查询。
- 列表接口不返回附件字节或完整附件元数据，只返回 `record_attachment_count`。

### 8.3 文件读取

新增：

- `GET /records/{id}/attachments/{attachment_id}`

规则：

- 当前附件和历史已移除附件都可以读取。
- 必须先校验用户有该记录详情权限，再校验附件的 `record_id` 与路径记录一致。
- 图片预览和普通下载均由前端通过 `context.api(..., { responseType: "raw" })` 获取 Blob；不直接绕过平台 API。
- 下载响应使用服务端确认后的 `Content-Type`、`X-Content-Type-Options: nosniff` 和安全编码的 `Content-Disposition` 文件名。
- 图片预览前端生成短生命周期 Blob URL；关闭预览或销毁抽屉时调用 `URL.revokeObjectURL()`。

## 9. 文件类型与校验

允许的扩展名：

- 图片：`.png`、`.jpg`、`.jpeg`、`.webp`
- Excel：`.xls`、`.xlsx`
- Word：`.doc`、`.docx`
- 压缩包：`.zip`

服务端必须完成以下校验，不能信任浏览器的扩展名或 `content_type`：

1. 文件名去除目录部分、NUL、控制字符和路径分隔符，trim 后长度为 1–255。
2. Base64 严格解码，拒绝空文件和非法编码。
3. 单文件解码后不超过 10 MiB。
4. 当前附件总数不超过 10，当前原始字节总量不超过 30 MiB。
5. 图片使用魔数核对 PNG、JPEG、WebP，不接受 SVG。
6. `.xls` 和 `.doc` 必须具有 OLE Compound File 头。两者共享容器签名且本功能不引入 Office 内容解析器，因此服务端统一保存为 `application/x-ole-storage`；扩展名只用于允许列表、文件名和界面图标，不作为可信内容分类。
7. `.xlsx` 和 `.docx` 必须为 ZIP 容器，并在不解压文件内容的前提下检查 `[Content_Types].xml` 以及 `xl/` 或 `word/` 目录标识；限制中央目录条目数量，防止畸形容器消耗资源。
8. `.xlsx` 和 `.docx` 不得包含 `vbaProject.bin` 或宏启用内容类型；显式宏格式 `.xlsm`、`.docm` 一律拒绝。
9. `.zip` 只校验 ZIP 容器结构，不解压、不读取成员正文、不执行任何内容。
10. 计算 SHA-256；若与该记录当前附件内容重复则拒绝，字段错误指向对应 `client_id`。

旧格式 `.xls`、`.doc` 使用 OLE 容器，可能包含宏，服务端在不解析业务内容的前提下无法区分具体 Office 类型或保证无宏，这是允许旧格式的明确限制。本功能只负责受控存储和下载，不提供恶意软件扫描；文件不会在服务端执行或自动打开，只有具备详情权限的用户主动下载后才由本机软件处理。

前端校验只用于即时反馈，后端校验是最终依据。前端不得依赖文件名决定是否把内容当图片展示，必须使用后端确认的 MIME 或本地文件对象的受支持图片类型。

## 10. 保存事务与审计

### 10.1 创建

创建服务流程：

1. 校验记录字段和附件请求。
2. 解码、校验全部新文件并计算哈希。
3. 在一个事务中创建主记录、报表/报送明细、附件行和创建审计。
4. 创建响应返回当前附件元数据。

任何一步失败都回滚，不留下孤立附件或半保存记录。

创建审计记录 `record_attachments: { "count": N, "ids": [...] }`；前端创建摘要仍只显示“创建”，不重复展开所有初始字段。

### 10.2 修改

修改服务流程：

1. 读取当前记录和当前附件，执行现有编辑权限及 `row_version` 校验。
2. 校验 `retained_ids` 与当前附件集合的关系。
3. 解码并校验新文件，合并保留附件后验证数量、总大小和内容去重。
4. 计算 `old_ids`、`new_ids`、`added_ids`、`removed_ids`。
5. 在现有原子更新事务中更新记录、标记移除附件、插入新附件、写审计并递增 `row_version`。

`changed_fields_json` 仅在集合变化时增加：

```json
{
  "record_attachments": {
    "changed": true,
    "old_ids": [12, 13],
    "new_ids": [13, 14],
    "added_ids": [14],
    "removed_ids": [12]
  }
}
```

审计 JSON 不保存文件字节，也不复制可变文件名；附件元数据不可变，由查询时根据 ID 补全。历史界面的新增、移除、保留标签只按当前审计的 `old_ids/new_ids` 计算，与附件行后来是否设置 `removed_at` 无关。只修改附件也必须形成 `action_code=update` 的审计并递增 `row_version`。

如果客户端提交的最终附件集合与当前集合完全相同，附件字段不计为变化，不因附件产生空修改审计。

### 10.3 删除

删除记录时，在现有删除事务中删除：

- 当前和历史记录附件；
- 现有确认附件；
- 审计、报表和报送明细；
- 主记录。

删除后记录本身不可访问，因此不再保留附件审计展示。

## 11. 权限

- 新建并添加附件：沿用 `report_special_processing.create`。
- 给已有记录增删附件：沿用现有 `can_edit` 和 `report_special_processing.edit`，状态限制不变。
- 查看、预览和下载当前或历史附件：沿用 `report_special_processing.detail`，且必须能查看所属记录。
- 已完成、已作废记录不可修改附件；重开后按现有编辑规则处理。
- 不新增能力码，不修改默认角色矩阵。

## 12. 登录超时联动

附件请求与登录恢复遵循独立设计中的平台协议：

- 新文件已经转换为 JSON 字符串请求体，属于可重放请求体。
- 只要保存请求包含 `record_attachments`，模块调用平台 API 时设置 `authPreflight: true`，在发送最多约 40 MiB 的 Base64 body 前先确认仍是原账号会话；该选项必须由平台剥离，不能成为 HTTP fetch 参数。
- 预检发现未认证时先显示原账号遮罩，成功后才发送附件 body；发现其他账号时不得发送，并进入注销退出流程；预检网络失败时保留表单和附件且不发送业务请求。
- 实际保存请求还必须由平台添加 `X-Auto-Check-Expected-User-Id`；后端在业务处理前与当前 session.user_id 原子比较，避免预检通过后其他标签页切换账号导致以错误身份保存。
- 保存请求收到带 `X-Auto-Check-Auth-Recovery: required` 的前置 401 时，抽屉、文件对象、缩略图和 JSON 请求体继续保留在当前标签页内。
- 原账号重新认证成功后，使用新 CSRF Token 自动重发完全相同的保存请求一次。
- 前置 401 保证第一次请求未进入模块处理器，因此不会重复创建记录或附件。
- 预检之后仍处理专用前置 401，以覆盖预检与保存之间会话恰好过期的竞态。
- 没有专用标识的业务 401、400、普通 409、500 或网络错误不自动重放；带 `account-mismatch` 的 409 由平台注销意外会话并进入 `discarding`，同样不重放且不交给模块处理。
- 下载通过平台 raw API，因此也继承同一重新认证能力。
- 主动刷新、关闭标签页或应用退出后，不恢复未保存附件。

## 13. 错误处理

- 不支持类型、文件损坏、空文件、文件名非法、单文件超限、数量超限、总量超限或内容重复：返回 400，错误字段为 `record_attachments` 或对应 `client_id`。
- retained ID 不属于当前记录、已被移除或重复：返回 400，不泄露其他记录附件信息。
- 编辑权限不足：返回 403。
- `row_version` 冲突：返回 409；前端保留附件和表单，提示用户刷新前确认是否复制未保存内容，不自动覆盖服务器版本。
- 数据库失败：事务回滚，返回现有内部错误结构。
- 网络失败：不自动重放写请求；表单和附件仍保留，由用户再次保存。
- 图片预览或附件下载失败：不影响记录详情其他内容，显示单项错误并允许重试。

所有错误路径都必须释放临时 Base64、FileReader、Blob URL 和事件监听器；密码或附件内容不得写入日志。

## 15. 测试设计

### 15.1 校验

- 每种允许类型的有效文件通过。
- 扩展名与文件头不匹配、非法 Base64、空文件、SVG、宏文件和可执行文件拒绝。
- 单个 10 MiB 边界通过，超过 1 字节拒绝。
- 10 个和总计 30 MiB 边界通过；第 11 个或总量超过 1 字节拒绝。
- 当前集合相同 SHA-256 拒绝；同名不同内容允许。
- OOXML 区分 XLSX 与 DOCX；畸形或超量 ZIP 中央目录拒绝。
- 新建省略附件字段兼容无附件；提供附件对象时缺少任一数组、重复 retained ID 或非法类型均拒绝。

### 15.2 仓储与事务

- 创建记录与附件同事务成功。
- 任一附件失败时不创建记录、附件或审计。
- 修改保留、添加、移除集合正确，内容行不可覆盖。
- 只改附件递增版本并写 update 审计。
- 版本冲突、权限失败或数据库异常不留下附件变化。
- 移除附件仍可按历史 ID 读取。
- 删除记录清理记录附件和确认附件。

### 15.3 API 与权限

- POST/PUT 的附件字段兼容省略、空集合和混合保留/新增。
- 越权 retained ID、跨记录下载、历史 ID 搭配错误 record ID 均拒绝。
- 详情只返回元数据，不返回字节。
- 下载保留 UTF-8 文件名、正确类型、长度和原字节。
- 审计分页批量补全修改前后元数据，不产生 N+1。
- 审计状态标签按每条审计的 old/new ID 集合计算，后续软删除不改变旧审计展示。
- 附件 JSON/Base64 在 45 MiB 路由上限内可进入处理；超过 45 MiB 由模块路由拒绝。
- 平台 50 MiB 保持最终硬上限，`void`、`reopen`、`status` 等非附件路由仍使用各自原请求上限。

### 15.4 前端

- 上传多选和剪贴板文件均进入同一附件状态管理。
- 纯文字粘贴不被拦截。
- 图片预览、Office/ZIP 文件卡片、删除、数量/大小提示正确。
- 同内容重复被前端提示，后端仍有最终校验。
- 保存请求只发送 retained ID 和新文件 Base64。
- 保存失败、普通业务 409 和登录恢复期间表单与附件保持不变；带 `account-mismatch` 的 409 由平台保持阻塞遮罩、注销意外会话并退出，不把响应交给附件模块。
- 编辑只读状态不出现添加和删除控件。
- 操作记录双栏正确标注新增、移除和保留。
- Blob URL 在关闭预览、关闭抽屉和模块 deactivate 时释放。

### 15.5 回归

- 现有确认说明及最多 3 张确认图片行为不变。
- 普通无附件新建、修改、确认、重开、作废、删除和导出不变。
- 现有能力码和状态权限不变。
- 登录超时后带附件保存只创建一条记录和一组附件。

## 16. 验收标准

1. 用户新建记录，粘贴图片并上传 Excel、Word、ZIP，保存后详情中能看到全部附件。
2. 用户编辑记录，移除一个旧附件并增加一个同名新内容文件，保存后当前附件正确。
3. 展开该次修改记录，可以在“修改前 / 修改后”两栏查看并下载旧、新附件。
4. 历史已移除图片仍可预览，Office/ZIP 仍可下载。
5. 只修改附件会增加一次修改审计并递增 `row_version`。
6. 非法类型、超限、重复内容和跨记录附件引用均被服务端拒绝，且不产生部分保存。
7. 登录超时发生在带附件保存时，原账号重新登录后自动保存一次，不丢附件、不重复记录。
8. 现有确认说明图片附件功能完全不变。
