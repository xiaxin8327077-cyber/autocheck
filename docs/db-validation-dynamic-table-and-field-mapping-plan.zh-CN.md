# 人行逐笔校验引擎动态表与字段映射改造方案

状态：方案已确认，待制定实施计划

适用范围：

- 工具 → 人行逐笔校验引擎
- 系统设置 → 人行逐笔校验引擎 → 刷新字段映射

## 一、需要解决的问题

本次只解决以下三个问题：

1. 逐笔表、模板表和公开信息表的物理表名写死。
2. 校验规则使用的英文字段名写死。
3. 系统设置刷新映射后，映射成功与未映射数量显示不正确，且无法查看最新映射关系。

接口发生异常时继续沿用现有错误提示机制，不在本次方案中重新设计接口异常处理。

## 二、问题一：物理表名写死

### 现状

逐笔表的 `ZG01`～`ZG13` 与物理表名关系由程序固定维护；模板表由程序预置物理表候选名；公开信息表由固定默认物理表名或物理表名配置驱动。配置中的实际物理表发生变化后，程序不能完全通过刷新映射切换到新表。

### 确定方案

三类业务表全部改为动态解析，程序不再保留生产业务物理表名，也不以旧物理表名作为运行兜底。

#### 逐笔表

- `ZG01`～`ZG13` 作为稳定逻辑表标识保留。
- 数据库迁移将当前十三条 `ZGXX → 逐笔物理表` 关系初始化到应用数据库映射表：

| 逐笔表 | 初始物理表 |
|---|---|
| `ZG01` | `zgxgzh_baseinfo_zg01_26` |
| `ZG02` | `zgxgzh_begraiseinfo_zg02_26` |
| `ZG03` | `zgxgzh_projendinfo_zg03_26` |
| `ZG04` | `zgxgzh_projholdinfo_zg04` |
| `ZG05` | `zgxgzh_projdebt_zg05_2024` |
| `ZG06` | `zgxgzh_beneficial_zg06` |
| `ZG07` | `zgxgzh_ioudetail_zg07` |
| `ZG08` | `zgxgzh_spvdetail_zg08` |
| `ZG09` | `zgxgzh_debtordate_zg09` |
| `ZG10` | `zgxgzh_surecinfo_zg10` |
| `ZG11` | `zgxgzh_industinfo_zg11` |
| `ZG12` | `zgzgzh_zg12` |
| `ZG13` | `zgzgzh_zg13` |

- 以上物理表名只作为数据库迁移的初始化数据存在，不再作为程序运行常量。
- 刷新时根据系统设置中的逐笔数据源、系统编号和分类编号读取源端配置，通过配置中的 `ZGXX` 关系更新自动映射。
- 管理员可以在映射关系弹框中人工修改任一 `ZGXX` 对应的物理表，例如将 `ZG01` 切换到新表。
- 人工覆盖优先于刷新取得的自动关系；再次刷新时保留人工覆盖，并检查人工指定的物理表是否仍然存在。
- 引擎、规则和前端表单只使用 `ZGXX`，不直接使用逐笔物理表名。
- 同一个 `ZGXX` 必须唯一对应一张当前生效物理表；缺失、重复或人工目标不存在时，在映射详情中明确显示并阻止受影响的逐笔校验。

#### 模板表

- 模板不再通过中文名匹配物理表。
- 模板关系以“逐笔表编号 + 信托产品类型口径”为稳定键，直接映射模板物理表。
- 映射关系持久化在应用数据库的映射表中，并允许管理员人工修改。
- 数据库迁移只初始化当前已有的四条模板关系：

| 逐笔表 | 信托产品类型口径 | 初始模板物理表 |
|---|---:|---|
| `ZG09` | `1` | `balance_sheet_info` |
| `ZG09` | `2` | `balance_sheet_info_zcglxt` |
| `ZG10` | `1` | `balance_sheet_info2` |
| `ZG10` | `2` | `balance_sheet_info2_zcglxt` |

- 以上物理表名只作为数据库迁移的初始化数据存在，不再作为程序运行常量。
- 后续模板物理表发生变化时，管理员在映射关系弹框中修改对应关系并保存，无需修改程序。
- 运行时先根据当前规则的 `ZG09` 或 `ZG10`，再根据当前逐笔记录的“信托产品类型口径”读取对应模板表关系。
- 关系缺失、重复或目标模板表不存在时，在映射详情中标记异常，并阻止受影响的模板校验。

#### 公开信息表

- 公开信息物理表关系持久化在应用数据库的映射表中，不再通过中文名查找。
- 数据库迁移将当前公开信息物理表 `public_information_rh` 初始化为默认映射关系。
- 该物理表名只作为数据库迁移的初始化数据存在，不再作为程序运行默认常量。
- 后续公开信息物理表发生变化时，管理员在映射关系弹框中修改并保存，无需修改程序。
- 运行时从当前生效的映射关系中取得公开信息物理表。
- 映射缺失或目标物理表不存在时，在映射详情中标记异常，并阻止已启用的公开信息校验。

#### 当期表与上期表

- 规则层只请求某个 `ZGXX` 的当期数据或上期数据，不接触物理表名。
- 若表配置关系包含报告期，则当期表和上期表均按 `ZGXX + 报告期` 解析。
- 若表配置关系只维护基础表，则上期表由表解析层统一按现有月份后缀规则生成。
- 上期表命名处理只能存在于表解析层，不得分散在具体规则中。

#### 运行一致性

- 刷新时一次性构建逐笔、模板和公开信息表目录。
- 每个校验任务在启动时取得一份映射快照。
- 同一个任务从开始到结束固定使用该快照。
- 任务执行期间的新刷新只对后续任务生效。

## 三、问题二：英文字段名写死

### 现状

部分规则直接读取固定英文字段，部分规则将固定英文字段放在中文字段之前。旧字段停用但未删除、新字段取得原中文业务名后，规则仍可能读取旧字段。

例如：旧字段 `a` 的中文名改为“项目编号-废弃”，新增字段 `a1` 的中文名为“项目编号”。刷新后，规则请求“项目编号”应读取 `a1`，不能因为旧字段 `a` 仍存在而继续读取 `a`。

### 确定方案

规则只声明中文业务字段名，通过最新字段信息关系动态解析当前英文字段。程序不保留写死英文字段兜底。

具体要求如下：

- 规则层只使用中文业务字段名。
- 映射层根据已解析出的实际物理表和中文字段名，从字段信息数据中定位当前英文字段名。
- 读取层使用解析得到的当前英文字段读取数据。
- 旧英文字段即使仍存在，只要它的中文名已经改为“废弃”或其他名称，就不能被原中文业务字段继续命中。
- 新英文字段取得原中文业务字段名并刷新后，后续任务直接使用新英文字段。
- 不允许通过旧英文字段名兜底。
- 不允许把新字段值覆盖到旧英文字段键上来兼容旧规则。
- 不允许规则直接读取业务英文字段。
- 跨表关联键、当期与上期匹配键、排序键、分组键、条件判断和结果明细均使用同一字段解析机制，不能只修改普通取值位置。
- ZG09、ZG10 现有模板指标与逐笔指标的编码转换和匹配逻辑属于正确规则，本次不得修改：ZG09 保留 `G001A → A_g00100` 一类转换及 `fb00001/fb00002` 指标匹配，ZG10 保留按 `H+5位数字` 指标编码匹配。
- 上述模板指标编码属于规则指标标识，不属于本方案要求清除的普通业务英文字段硬编码。

### 规则必需字段

为每个 `ZGXX`、模板校验和公开信息校验整理规则实际需要的中文字段集合。

该集合只用于两个目的：

1. 校验任务开始前检查本次规则所需字段是否全部能够映射。
2. 在映射详情中标识哪些字段属于规则必需字段。

如果本次所选表存在规则必需字段无法映射，则阻止对应校验启动，并明确显示表和中文字段名。业务表中存在其他未映射物理字段时，不阻止执行。

## 四、问题三：映射数量显示错误且无法查看映射关系

### 现状

当前刷新结果中的未映射数量没有根据实际业务表物理字段计算，可能始终显示“未映射 0 个字段”。页面只能看到汇总状态，无法确认每张表的物理字段实际映射到了哪个中文字段。

### 确定方案

映射结果、映射明细、人工覆盖关系和修改记录全部持久化到应用数据库，不再只保存在应用进程内存中。刷新映射时，同时读取三类实际业务表的物理列，并与字段信息关系进行比对，生成真实的已映射和未映射统计。

#### 统计对象

统计范围包括：

- `ZG01`～`ZG13` 解析出的逐笔物理表；
- 通过 `ZG09/ZG10 + 信托产品类型口径` 映射出的模板物理表；
- 通过应用数据库映射关系取得的公开信息物理表。

统计以实际业务表的物理字段为基准：

- 实际物理字段能够在当前表的字段信息关系中找到有效中文字段名，计为“已映射”。
- 实际物理字段无法找到有效中文字段名，计为“未映射”。
- 字段信息中存在记录，但实际业务表中不存在对应物理字段，作为“配置字段不存在”单独展示，不计入实际物理字段的已映射或未映射数量。

#### 系统技术字段

主键、创建时间、更新时间、删除标记等统一维护的系统技术字段不计入业务字段映射统计。

系统技术字段排除清单集中维护，映射详情中不作为未映射字段展示。不得在不同表或不同页面分别维护排除逻辑。

#### 汇总状态

刷新完成后显示：

- 已解析表数量；
- 实际业务字段总数；
- 已映射字段数量；
- 未映射字段数量；
- 规则必需字段缺失数量；
- 配置字段不存在数量；
- 刷新时间；
- 刷新来源。

未映射字段存在时，刷新仍可完成，并准确显示数量。只有本次校验所选表存在规则必需字段无法映射时，才阻止校验执行。

接口查询、连接或读取异常继续使用当前错误提示机制；本次不改变接口异常处理方案。

#### 查看最新映射关系按钮

在系统设置的“刷新字段映射”按钮旁新增“查看最新映射关系”按钮。

按钮展示最近一次成功构建的映射快照。没有成功快照时，按钮可以打开空状态弹框，明确提示尚无可查看的映射关系。

#### 映射详情弹框

弹框按以下层级查看：

1. 表类型：逐笔、模板、公开信息。
2. 逻辑表：`ZGXX`、模板对应的 `ZG编号 + 信托产品类型口径`，或固定逻辑标识“公开信息”。
3. 实际物理表。
4. 字段映射明细。

每张表显示：

- 表类型；
- 逻辑表标识或中文名；
- 当前物理表名；
- 业务物理字段总数；
- 已映射数量；
- 未映射数量；
- 规则必需字段缺失数量；
- 配置字段不存在数量。

每个字段显示：

- 实际英文字段名；
- 当前中文字段名；
- 映射状态；
- 是否属于规则必需字段；
- 状态说明。

字段状态固定为：

- 已映射；
- 未映射；
- 规则必需字段缺失；
- 配置字段不存在。

弹框支持按表类型、逻辑表和映射状态筛选，默认优先展示未映射、规则必需字段缺失和配置字段不存在项。

#### 人工修改与保存

映射详情弹框支持管理员人工修改并保存以下关系：

- `ZGXX → 逐笔物理表`；
- `ZG09/ZG10 + 信托产品类型口径 → 模板物理表`；
- `公开信息 → 公开信息物理表`；
- `逻辑表 + 中文业务字段名 → 实际英文字段名`。

人工修改不回写源端 `baseinfo` 和 `field_info`，而是作为人工覆盖关系保存到应用数据库。执行时，人工覆盖关系优先于自动刷新取得的关系。

每次人工保存必须填写修改原因，并记录：

- 修改对象；
- 修改前的自动映射值；
- 修改后的人工映射值；
- 修改人；
- 修改时间；
- 修改原因。

支持对单条人工覆盖执行“恢复自动映射”。恢复后删除该条覆盖的生效状态，后续执行重新使用最近一次自动刷新得到的关系，同时保留历史修改记录。

再次刷新时保留已有人工覆盖。若源端关系已经变化，或人工覆盖指向的物理表、物理字段已不存在，则将该覆盖标记为冲突，在映射详情中提示管理员处理；不得静默改用其他关系。

#### 持久化内容

应用数据库至少保存：

- 十三条初始逐笔表映射关系；
- 每次成功刷新形成的映射快照及刷新时间；
- 当前生效的表映射和字段映射明细；
- 实际字段的已映射、未映射及异常状态；
- 当前人工覆盖关系；
- 人工修改历史；
- 四条初始模板映射关系；
- 一条初始公开信息表映射关系：`公开信息 → public_information_rh`。

新增映射表结构和表级初始化数据必须保存为项目中的独立 SQL 文件，作为可审查、可重复执行的数据库交付物。SQL 初始化内容只包括：

- 当前十三条 `ZG01`～`ZG13` 逐笔表关系；
- 当前四条模板表关系；
- 当前一条公开信息表关系。

SQL 文件不得初始化字段映射明细。字段映射必须在管理员点击“刷新字段映射”且刷新流程成功完成后，根据源端表配置、字段信息和实际业务表物理列生成，并保存到应用数据库。

应用重启后直接加载最近一次成功快照和当前人工覆盖关系，“查看最新映射关系”仍可查看，不依赖进程内存是否保留。

## 五、统一刷新流程

“刷新字段映射”实际刷新完整的表与字段映射快照，按以下顺序完成：

1. 根据系统设置读取逐笔表配置。
2. 解析 `ZGXX → 逐笔物理表`。
3. 从应用数据库读取 `ZG09/ZG10 + 信托产品类型口径 → 模板物理表` 的关系。
4. 从应用数据库读取 `公开信息 → 公开信息物理表` 的关系。
5. 读取三类实际业务表的物理列。
6. 读取各表对应的字段信息关系。
7. 排除系统技术字段。
8. 生成实际物理字段的已映射和未映射明细。
9. 检查各规则必需中文字段是否可解析。
10. 合并应用数据库中已保存的人工覆盖关系。
11. 检查人工覆盖目标是否仍然存在，并标记冲突。
12. 生成汇总状态和按表映射详情。
13. 所有数据构建完成后，将新快照及字段映射明细在同一数据库事务中整体保存到应用数据库，并切换为当前快照；刷新失败时不得写入半成品字段映射。

不得分别缓存表名和字段名，也不得让系统设置页、工具页或执行任务各自维护独立映射。

## 六、界面行为

### 系统设置页

- 保留“刷新字段映射”按钮。
- 在其旁边增加“查看最新映射关系”按钮。
- 刷新期间禁用两个按钮，避免读取半完成状态。
- 刷新完成后立即更新真实汇总数量。
- 存在未映射字段时显示未映射数量，但不把正常完成的刷新提示为接口失败。
- 接口异常时继续显示现有异常信息。

### 工具页

- 打开人行逐笔校验引擎时读取同一映射快照状态。
- 开始校验前，仅检查本次所选逐笔表以及已启用的模板、公开信息校验所需字段。
- 存在规则必需字段缺失时阻止启动，并提示前往系统设置刷新或查看映射关系。
- 仅存在非规则必需的未映射字段时允许执行。

## 七、实施约束

- 不修改具体校验规则的判断标准。
- 不修改 ZG09、ZG10 模板指标与逐笔指标的现有编码转换和匹配逻辑。
- 不改变校验结果文件的业务字段含义。
- 不使用模糊匹配推断表或字段。
- 不保留生产业务物理表名兜底。
- 不保留生产业务英文字段名兜底。
- 元数据表自身的结构列名不属于业务物理表和业务英文字段硬编码，但应由明确的数据访问层集中使用。
- 增加自动化检查，防止规则重新直接引用生产业务物理表名或英文字段名。
- 新增映射表 DDL 和表级初始化数据必须保存为独立 SQL 文件；字段映射明细不得写入初始化 SQL。

## 八、验收标准

1. 当前十三条 `ZG01`～`ZG13` 物理表关系只存在于应用数据库初始化数据中，不再作为程序运行常量。
2. 刷新能够从源端配置更新逐笔表自动关系，人工覆盖能够单独变更任一逐笔表（包括 `ZG01`）并优先生效。
3. 模板的四条初始物理表关系只存在于应用数据库初始化数据中，不再作为程序运行常量。
4. 模板按 `ZG09/ZG10 + 信托产品类型口径` 从映射表取得当前物理表。
5. 程序不再维护公开信息的生产物理表名。
6. 修改映射关系并保存后，后续任务使用新物理表或新字段，无需修改程序。
7. 规则只通过中文业务字段名取得当前英文字段。
8. 旧字段改为“废弃”、新字段取得原中文名后，刷新即可切换到新字段。
9. 未映射数量以实际业务表物理字段为基准准确统计。
10. 系统技术字段不计入映射统计。
11. “查看最新映射关系”能够按逐笔、模板、公开信息及具体表查看字段明细并人工修改保存。
12. 人工覆盖不修改源端元数据，刷新后继续保留；无效覆盖能够显示冲突。
13. 人工修改记录包含修改人、时间、前后值和原因，并支持单条恢复自动映射。
14. 应用重启后仍可查看和使用最近一次成功映射快照。
15. 规则必需字段未映射时阻止对应校验；其他未映射字段不阻止执行。
16. 接口异常继续正确显示现有错误信息。
17. 系统设置页、工具页和执行任务使用同一映射快照。
18. 新增映射表结构及十八条表级初始关系保存在独立 SQL 文件中：十三条逐笔、四条模板、一条公开信息；不包含任何字段映射明细。
19. 初始安装后字段映射明细为空；点击“刷新字段映射”成功后，字段明细在同一事务中保存到应用数据库。
20. 刷新失败时数据库中不产生半成品字段映射，上一份成功快照保持不变。
21. 逐笔校验相关测试及项目全量测试通过。

## 九、不在本方案范围内

- 不重新设计接口异常提示机制。
- 不允许用户在运行时直接选择生产物理表名或英文字段名。
- 不修改规则业务条件、阈值及输出口径。
- 不在本方案中实施代码改造；代码实施应在本方案评审通过后另行制定实施计划。
